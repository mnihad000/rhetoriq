# RhetoriQ Operations Runbook

For the B5 specialized-store stack, use the authenticated TLS overlay and procedures in [B5 operations and B6 handoff](B5_OPERATIONS.md). `/health` remains process liveness; `/health/b5` and `/api/research/health` report dependency availability, projection lag and degraded readiness. Actual-stack qualification remains pending.

## Start and readiness

Configure fresh local values for `POSTGRES_PASSWORD` and `SEARXNG_SECRET`, then run:

```powershell
docker compose config
docker compose up --build -d
docker compose ps
```

`topic-init` must finish successfully before the API, outbox publisher, or workers are considered ready. Check `GET http://localhost:8000/api/research/health`; Kafka, schema registry, outbox, consumer groups, checkpointer, SearXNG, and the investigation worker must be ready. Consumer lag and DLQ totals must be numeric.

## Services and failure behavior

- `api` writes business mutations and outbound events atomically. Stored ingestion and investigation-run requests return HTTP 202.
- `outbox-publisher` publishes committed rows with idempotence and `acks=all`.
- `document-worker`, `signal-worker`, `investigation-worker`, and `projection-worker` use distinct consumer groups and manual offset commits.
- Kafka or registry failure degrades readiness and grows the durable outbox backlog. It never activates a synchronous fallback.
- Transient consumer failures use bounded exponential backoff with jitter. Schema, validation, policy, and permanent parsing failures go directly to the topic’s DLQ.
- If DLQ publication fails, the source offset is not committed.

## Inspection

```powershell
docker compose logs topic-init
docker compose logs outbox-publisher
docker compose logs document-worker signal-worker investigation-worker projection-worker
docker compose exec broker /opt/kafka/bin/kafka-topics.sh --bootstrap-server broker:19092 --list
```

Use the research health response for outbox pending/retrying counts, total publish and consumption attempts, consumer-group state, aggregate/per-group lag, and per-DLQ record counts. Do not log event bodies while diagnosing credentials or policy failures.

## Controlled replay

Every replay requires an explicit primary topic, partition, start offset, and audited replay job ID generated by the CLI. Use a dry run first:

```powershell
cd backend
..\.venv\Scripts\python.exe -m events.replay --topic raw.documents.v1 --partition 0 --start-offset 0 --end-offset 100 --dry-run
..\.venv\Scripts\python.exe -m events.replay --topic raw.documents.v1 --partition 0 --start-offset 0 --end-offset 100
```

Use `--correlation-id` to narrow a range. Replay uses normal handlers and stable domain IDs. It does not commit normal consumer offsets and must not duplicate investigations, notifications, documents, or completion records.

## Recovery sequence

1. Restore Kafka and Apicurio health without modifying outbox rows.
2. Confirm `topic-init` can list/register all 12 subjects and that compatibility remains `BACKWARD_TRANSITIVE`.
3. Restart the outbox publisher, then document, signal, investigation, and projection workers.
4. Watch backlog and lag fall; inspect DLQs before replaying anything.
5. Replay only an explicit, reviewed range. Preserve the replay job record.
6. Verify the correlated workspace, research trail, artifact hash, and completion event count.

Worker restart recovery relies on durable offsets, consumer ledgers, stable event IDs, domain upserts, and investigation leases. Never repair a stuck run by manually deleting ledger or outbox rows.

## Retention and secrets

Topic defaults are 7 days for raw documents, 30 days for processed documents, 90 days for signals/requests/stages, 180 days for completed investigations, and 14 days for DLQs. Provider policy may shorten but never extend these values.

Kafka/SASL/TLS, model, database, Redis, and provider credentials belong only in environment or platform secret configuration. They must not appear in events, DLQs, logs, fixtures, or committed diagnostic scripts. If a credential is exposed, remove it from source and rotate it at the provider; code removal alone does not revoke it.

## Host prerequisite

Docker Desktop’s Linux engine requires WSL 2/Virtual Machine Platform and firmware virtualization. If Docker reports `HCS_E_HYPERV_NOT_INSTALLED`, run `wsl --install --no-distribution` from an elevated terminal, restart Windows, and verify `docker version` shows a server version before starting Compose.
